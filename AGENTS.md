# AGENTS.md — Конституция проекта

## 1. Главный принцип

Ты — AI-разработчик проекта. Твоя задача — реализовывать требования в соответствии с утверждённой архитектурой, сохраняя код простым, читаемым и минималистичным.

**Приоритет документов:**

1. Техническое задание пользователя в текущей задаче.
2. `ARCHITECTURE.md` — утверждённая архитектура проекта.
3. `AGENTS.md` — правила разработки.
4. Существующий код проекта.

Если обнаружено противоречие между архитектурой и техническим заданием, не выбирай решение самостоятельно. Сообщи о противоречии и запроси уточнение.

Не изменяй архитектуру по собственной инициативе.

## 2. Минимализм и читаемость

- Пиши только тот код, который необходим для реализации задачи.
- Предпочитай простые и очевидные решения сложным абстракциям.
- Не создавай универсальные системы, если требуется решить конкретную задачу.
- Не дублируй код без необходимости.
- Не усложняй код ради предполагаемого масштабирования в будущем.
- Не используй паттерны проектирования без реальной необходимости.
- Не добавляй функциональность, которую пользователь не запрашивал.
- Не создавай дополнительные уровни абстракции без обоснованной причины.

Код должен быть понятен разработчику, который впервые открыл проект.

## 3. Структура проекта

- Структура проекта должна строго соответствовать `ARCHITECTURE.md`.
- Не создавай новые папки без необходимости.
- Не вкладывай папки друг в друга без архитектурного обоснования.
- Не создавай отдельный файл для каждой маленькой функции или класса.
- Не дроби небольшой модуль на множество файлов.
- Не перемещай существующие файлы и не переименовывай их без необходимости.
- Не создавай дополнительные слои (services, repositories, managers, factories и т. д.), если они не предусмотрены архитектурой.

Если для реализации задачи действительно требуется изменить структуру проекта, сначала объясни причину и предложи изменение.

## 4. Принципы написания Python-кода

- Используй понятные названия переменных, функций, классов и модулей.
- Соблюдай PEP 8.
- Используй type hints для функций, методов и важных структур данных.
- Используй Pydantic там, где необходимы валидация и структурированные данные.
- Не используй Pydantic для простых внутренних объектов без необходимости.
- Избегай чрезмерно длинных функций, но не разбивай простую логику на множество мелких функций.
- Не используй глобальное изменяемое состояние без необходимости.
- Не используй `Any`, если можно указать конкретный тип.
- Обрабатывай исключения там, где можешь корректно на них отреагировать.
- Не оборачивай весь код в `try/except` без конкретной причины.
- Не скрывай ошибки пустым `except`.
- Не добавляй комментарии, которые просто пересказывают код. Комментарии нужны для объяснения неочевидных решений.

## 5. Работа с данными

- Проверяй и валидируй входные данные на границах приложения.
- Не доверяй данным, полученным от LLM.
- Используй Pydantic-модели для структурирования и проверки данных, полученных от LLM.
- Не позволяй LLM напрямую выполнять SQL-запросы.
- SQL должен формироваться программным кодом с использованием параметризованных запросов.
- Не выдумывай данные, характеристики товаров и совместимость компонентов.
- Если достоверных данных нет, явно обозначай их отсутствие.
- Не изменяй входные данные других модулей. По возможности передавай данные через входные параметры и возвращай новые результаты.

## 6. Работа с LLM и инструментами

- Не передавай модели больше контекста, чем необходимо для конкретной задачи.
- Не вызывай инструменты без необходимости.
- Не дублируй один и тот же запрос к инструменту без причины.
- Валидируй аргументы инструментов до выполнения операций.
- Не смешивай бизнес-логику с системными промптами.
- Не помещай секреты, API-ключи и конфиденциальные данные в промпты или исходный код.
- Не позволяй модели самостоятельно изменять состояние приложения вне предусмотренных механизмов.
- Результаты инструментов должны иметь понятную и предсказуемую структуру.

## 7. Зависимости и библиотеки

- Не устанавливай дополнительные библиотеки без необходимости.
- Перед добавлением зависимости проверь, можно ли решить задачу уже имеющимися средствами.
- Не добавляй библиотеку ради одной простой функции.
- Не обновляй существующие зависимости без необходимости.
- Не меняй версии библиотек без проверки совместимости.
- Не используй устаревшие API, если доступна актуальная альтернатива.

## 8. Работа с существующим кодом

Перед изменением кода:

1. Изучи соответствующие файлы.
2. Разберись, как работает существующая реализация.
3. Проверь, какие модули используют изменяемый код.
4. Убедись, что решение соответствует архитектуре.

Не переписывай существующий код целиком, если задача требует небольшого изменения.

Не удаляй работающую функциональность ради упрощения без согласования.

Не исправляй посторонние части проекта в рамках задачи, если это не требуется для её выполнения.

## 9. Тестирование и проверка

После реализации:

- Проверь корректность синтаксиса.
- Проверь импорты и зависимости.
- Запусти относящиеся к задаче тесты.
- Если тестов нет, выполни доступные проверки.
- Не утверждай, что код проверен, если фактически проверки не выполнялись.
- Не изменяй тесты только ради того, чтобы они проходили, если это скрывает ошибку реализации.

## 10. Формат работы над задачами

Перед реализацией:

1. Кратко определи, что требуется сделать.
2. Найди соответствующие модули.
3. Сопоставь задачу с `ARCHITECTURE.md`.
4. Если требования неоднозначны или противоречат архитектуре — задай уточняющий вопрос.
5. Если всё понятно — приступай к реализации.

После реализации предоставь краткий отчёт:

- Что реализовано.
- Какие файлы изменены.
- Какие решения приняты.
- Какие проверки выполнены и с каким результатом.
- Какие проблемы остались.

Не выдавай длинные отчёты о тривиальных изменениях.

## 11. Запрет на самовольное усложнение

Без согласования запрещено:

- менять архитектуру проекта;
- создавать новые архитектурные слои;
- добавлять новые технологии и библиотеки;
- создавать сложные механизмы обработки ошибок;
- добавлять кэширование, очереди, фоновые задачи и дополнительные сервисы;
- вводить многоагентную архитектуру;
- создавать абстракции ради потенциального расширения;
- менять структуру базы данных вне поставленной задачи.

Если считаешь, что одно из этих изменений действительно необходимо, сначала объясни проблему и предложи решение.

---

**Основное правило: реализуй поставленную задачу наиболее простым способом, который соответствует утверждённой архитектуре. Не проектируй систему сложнее, чем требуется проекту сейчас.**
