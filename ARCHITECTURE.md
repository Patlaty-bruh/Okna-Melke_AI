# ARCHITECTURE.md — Архитектура AI-агента Melke

## 1. Назначение проекта

Проект представляет собой AI-агента-консультанта по подбору пластиковых окон и комплектующих компании Melke.

Главная задача агента — помочь клиенту подобрать подходящее оконное решение на основе его потребностей, предпочтений, условий эксплуатации и бюджета, ответить на вопросы о продукции и компании, а затем передать заинтересованного клиента менеджеру.

Агент должен вести естественный диалог, постепенно собирать информацию о клиенте и использовать её для подбора продукции.

Агент не должен превращать диалог в анкету. Он самостоятельно определяет, какие сведения уже известны, чего не хватает и какой вопрос необходимо задать следующим.

## 2. Конечная цель и сценарий работы

Конечная цель агента — довести клиента до передачи менеджеру с подготовленным контекстом обращения.

Основной сценарий:

1. Клиент начинает диалог.
2. Агент определяет намерение клиента и понимает, какая помощь ему требуется.
3. Агент выясняет условия эксплуатации окна, пожелания и бюджет.
4. Агент сохраняет полученную информацию в State.
5. При необходимости обращается к базе данных для поиска продукции.
6. При необходимости обращается к RAG для получения информации о компании, продукции и технологиях.
7. Сравнивает найденные варианты и объясняет рекомендации.
8. При необходимости предоставляет ссылку на калькулятор Melke.
9. Отвечает на дополнительные вопросы и корректирует подбор.
10. Когда клиент готов продолжить оформление, предлагает связаться с менеджером.
11. Передаёт менеджеру собранный контекст обращения.

Агент не оформляет оплату, не заключает договор и не запускает сделку самостоятельно.

На этапе MVP передача менеджеру может быть реализована заглушкой, которая фиксирует факт передачи и подготовленные данные.

### Основные функции агента

- Консультирование по продукции Melke.
- Сбор предпочтений и условий эксплуатации.
- Подбор профильных систем и комплектующих.
- Поиск и сравнение вариантов в каталоге.
- Объяснение различий между вариантами.
- Ответы на вопросы о компании, технологиях, гарантии, доставке, замере и монтаже.
- Предоставление ссылки на калькулятор.
- Подготовка данных для менеджера.
- Передача заинтересованного клиента менеджеру.

## 3. Общая архитектура

В основе проекта используется LangGraph.

Основной управляющий компонент — LLM-агент, который анализирует сообщения клиента, учитывает текущее состояние диалога и принимает решение о необходимости вызова инструментов.

Агент имеет доступ к следующим инструментам:

- `search_products` — поиск продукции в PostgreSQL.
- `search_knowledge` — поиск информации через RAG.
- `get_calculator_link` — получение ссылки на калькулятор Melke.
- `get_manager` — передача обращения менеджеру.
- `save_customer_profile` — сохранение в State сведений, которые клиент сообщил о себе (§5.5).

Инструменты вызываются только тогда, когда это необходимо для решения текущей задачи.

Общая схема:

```text
                    START
                      |
                      v
                 Получение State
                      |
                      v
                 Agent (LLM)
                      |
          Анализ сообщения и контекста
                      |
          Определение необходимых действий
                      |
                      v
                 Tool Calls?
                  /       \
                Да         Нет
                |           |
                v           v
           Выполнение     Формирование
           инструментов   ответа
                |           |
                v           |
          Получение         |
          результатов       |
                |           |
                v           |
             Agent <--------+
                |
                v
         Формирование ответа
                |
                v
         Обновление State
                |
                v
                END
```

Если требуется несколько независимых инструментов, они могут выполняться параллельно.

Например, при вопросе о различиях профильных систем агент может одновременно обратиться к PostgreSQL и RAG.

Если результат одного инструмента необходим для вызова другого, инструменты выполняются последовательно.

## 4. State — состояние диалога

State содержит актуальный контекст клиента и информацию, необходимую для продолжения диалога.

State должен позволять агенту понимать:

- кто обращается;
- что клиент уже рассказал о своих потребностях;
- какие предпочтения и ограничения известны;
- какие товары были найдены или выбраны;
- какие вопросы уже обсуждались;
- готов ли клиент перейти к менеджеру.

State не должен превращаться в хранилище всех данных проекта. В нём хранится только информация, необходимая для работы текущего диалога.

Основные логические группы данных:

### User

Информация о пользователе и его контексте.

### CustomerPreferences

Предпочтения клиента:

- цвет профиля;
- ламинация;
- форма окна;
- количество створок;
- тип открывания;
- тип стеклопакета;
- фурнитура;
- дополнительные комплектующие;
- пожелания к теплозащите;
- пожелания к звукоизоляции;

Не все перечисленные параметры обязательно должны быть заполнены.

### CustomerContext

Условия и ограничения заказа:

- бюджет;
- валюта;
- тип объекта;
- категория продукции;
- количество окон;
- условия эксплуатации;
- информация о юридическом лице, если применимо.

### Conversation

История сообщений и последнее сообщение клиента. (Последние 25 сообщений)

### SearchResults

Актуальные результаты поиска продукции и контекст, полученный из RAG.

### ManagerHandoff

Состояние передачи менеджеру.

Состояние клиента должно обновляться на основании новых сообщений. Уже полученные сведения не должны теряться при поступлении следующего сообщения.

Отсутствующие сведения не нужно заполнять предположениями.

### Реализация State (MVP)

State реализован в `state.py` как `TypedDict` и содержит:

- `user` — `User` (`ContextUser` с вложенным `Preferences`, `ContactInfo`);
- `messages` — история диалога (`add_messages`), в модель передаются последние 25 сообщений;
- `last_user_message` — последнее сообщение клиента;
- `candidate_products` — результаты поиска продукции (заполнение — следующий этап);
- `manager_handoff` — состояние и данные передачи менеджеру;
- `calculator_url` — ссылка на калькулятор, полученная в текущем диалоге.

State хранится в памяти процесса (`Agent`), между перезапусками и в БД не сохраняется (решение для MVP).

## 5. Инструменты агента

### 5.1. search_products — поиск продукции в PostgreSQL

Назначение:

Поиск профильных систем, стеклопакетов, ламинации, фурнитуры и готовых оконных конфигураций.

Инструмент используется, когда клиент:

- спрашивает о конкретных товарах;
- хочет сравнить профильные системы;
- хочет подобрать окно;
- называет технические характеристики;
- сообщает бюджет и пожелания, по которым нужно подобрать варианты;
- просит показать доступные компоненты или конфигурации.

Не нужно обращаться к БД при каждом сообщении. Например, вопрос «Какая гарантия на окна?» не требует поиска в каталоге.

#### Данные для вызова

LLM формирует структурированный JSON с критериями поиска.

Возможные данные:

- категория продукции;
- названия профильных систем;
- типы стеклопакетов;
- названия ламинации;
- производитель или модель фурнитуры;
- минимальное значение теплозащиты, если оно используется как критерий;
- бюджетные ограничения;
- обязательные требования;
- предпочтения для ранжирования;
- количество результатов.

Пример структуры:

```json
{
  "product_category": "window",
  "filters": {
    "profile_names": ["Melke Centum"],
    "lamination_names": ["Золотой дуб"],
    "is_heat_saving": true
  },
  "preferences": {
    "thermal_protection": "high",
    "budget_level": "medium"
  },
  "limit": 5
}
```

Это пример формата, а не окончательная Pydantic-модель. Точный набор допустимых полей должен соответствовать реальной схеме БД.

#### Генерация запроса моделью

Для генерации JSON-запроса к БД используется отдельный вызов LLM.

К этому вызову обязательно прикрепляется специальная инструкция, содержащая:

1. Назначение поиска.
2. Схему базы данных.
3. Названия таблиц.
4. Названия колонок.
5. Типы данных колонок.
6. Связи между таблицами.
7. Допустимые значения полей.
8. Правила формирования фильтров.
9. Разницу между обязательными ограничениями и предпочтениями.
10. Формат JSON, который необходимо вернуть.

Модель должна использовать только существующие таблицы и поля.

Она не должна придумывать отсутствующие характеристики, значения или связи.

Если клиент не сообщил необходимое значение, модель должна оставить соответствующее поле пустым (`null`) или не включать его в запрос.

Модель не должна подставлять предполагаемые характеристики вместо неизвестных.

#### Проверка и обработка JSON

Сгенерированный JSON обязательно проходит программную проверку.

Алгоритм обработки:

1. Получает ответ модели.
2. Удаляет Markdown-обрамление, если модель вернула JSON внутри блока кода.
3. Удаляет лишний текст до и после JSON, если это возможно сделать однозначно.
4. Проверяет корректность синтаксиса JSON.
5. Если обнаружены незначительные ошибки формата, пытается выполнить ограниченное исправление.
6. Проверяет структуру через Pydantic-модель.
7. Проверяет допустимость названий полей и значений.
8. Проверяет логическую корректность фильтров.
9. При успешной проверке передаёт данные в функцию формирования SQL-запроса.
10. При невозможности корректно восстановить или проверить запрос не выполняет обращение к БД.

Исправление JSON не должно менять смысл запроса или самостоятельно придумывать отсутствующие значения.

Если JSON невозможно восстановить безопасно, поиск не выполняется: инструмент возвращает статус `error`, а агент честно сообщает клиенту, что данные получить не удалось. Повторный вызов модели для исправления JSON в MVP не выполняется (решение заказчика).

Не допускать бесконечных повторных попыток.

#### Формирование SQL

LLM не выполняет SQL самостоятельно.

После проверки JSON Python формирует SQL-запрос на основании заранее определённых правил.

Требования:

- использовать параметризованные запросы;
- использовать только разрешённые таблицы и колонки;
- не допускать произвольного SQL от LLM;
- проверять совместимость компонентов по таблицам совместимости;
- не считать неподтверждённую совместимость доказанной;
- не возвращать характеристики, которых нет в БД.

После выполнения запроса результаты передаются обратно агенту.

#### Фильтрация и ранжирование

Подбор должен состоять из двух этапов:

1. Фильтрация по обязательным требованиям клиента.
2. Ранжирование оставшихся вариантов по предпочтениям.

Проверка и ранжирование выполняются алгоритмом на Python, а не самой LLM.

LLM получает результаты и объясняет клиенту различия между ними.

Модель не должна самостоятельно менять результаты фильтрации или выдавать неподтверждённые варианты как подходящие.

### 5.2. search_knowledge — поиск через RAG

Назначение:

Получение информации из базы знаний компании.

Инструмент используется, когда клиент спрашивает о:

- компании Melke;
- технологиях производства;
- свойствах продукции;
- гарантиях;
- условиях заказа;
- доставке;
- замере;
- монтаже;
- эксплуатации окон;
- других вопросах, ответы на которые находятся в документации компании.

RAG не заменяет структурированную базу данных каталога.

#### Данные для вызова

LLM формирует поисковый запрос на основании текущего сообщения и контекста диалога.

Возможная структура:

```json
{
  "query": "Какие гарантийные условия действуют на окна Melke?",
  "categories": ["warranty"],
  "product_names": [],
  "limit": 5
}
```

Возможные категории:

- `company`;
- `products`;
- `warranty`;
- `delivery`;
- `installation`;
- `measurement`;
- `ordering`;
- `technology`.

Категории являются фильтрами по метаданным документов, если соответствующие метаданные предусмотрены RAG-хранилищем.

Если сообщение содержит местоимения или ссылки на предыдущие сообщения, модель должна сформировать самостоятельный поисковый запрос с учётом контекста.

Например:

Сообщение клиента: «А какие у них гарантии?»

Поисковый запрос: «Какие гарантийные условия действуют на пластиковые окна Melke?»

#### Работа RAG

1. Получает сформированный запрос.
2. Выполняет поиск по векторному индексу.
3. При необходимости использует гибридный поиск.
4. Возвращает наиболее релевантные фрагменты.
5. Передаёт найденный контекст агенту.

Агент формирует ответ на основании полученных документов.

Если в базе знаний нет достаточной информации, агент должен сообщить об этом, а не придумывать ответ.

### 5.3. get_calculator_link — получение ссылки на калькулятор

Назначение:

Предоставление клиенту ссылки на официальный калькулятор Melke.

Инструмент вызывается, когда клиент:

- спрашивает стоимость окна;
- хочет рассчитать стоимость;
- интересуется окончательной ценой;
- хочет самостоятельно изменить параметры и посмотреть стоимость.

Инструмент не рассчитывает стоимость самостоятельно.

Ссылка хранится в конфигурации приложения, а не непосредственно в системном промпте.

Для вызова не требуется сложный набор параметров. Если используется один калькулятор, достаточно самого вызова инструмента.

Если в будущем появятся разные калькуляторы для разных категорий продукции, инструмент сможет принимать категорию продукции.

После вызова агент объясняет клиенту, что по ссылке можно выполнить расчёт.

### 5.4. get_manager — передача менеджеру

Назначение:

Передача заинтересованного клиента менеджеру для продолжения работы.

Инструмент вызывается, когда:

- клиент явно хочет связаться с менеджером;
- клиент готов продолжить оформление заказа;
- требуется индивидуальный расчёт;
- нужна консультация, которую агент не может предоставить;
- необходимо уточнить техническую совместимость или возможность изготовления;
- вопрос требует участия специалиста компании.

#### Данные для вызова

Инструмент должен получить подготовленный контекст обращения:

- идентификатор пользователя;
- предпочтения клиента;
- бюджет, если известен;
- условия эксплуатации;
- выбранные или найденные товары;
- историю или краткое содержание диалога;
- причину передачи менеджеру;
- контактные данные, если они были предоставлены.

Необязательные сведения не должны блокировать передачу менеджеру.

Инструмент не должен выдумывать контактные данные или характеристики заказа.

На этапе MVP реализована заглушка: инструмент `get_manager` фиксирует обращение в State
(`manager_handoff.status = pending`, причина в `additional_comment`) и в лог приложения;
отправка менеджеру не выполняется. Контекст обращения хранится в State и собирается Python,
а не моделью.

### 5.5. save_customer_profile — сохранение сведений о клиенте

Назначение:

Сохранение в State предпочтений, контекста заказа и контактных данных, которые клиент сообщил в диалоге.

Инструмент вызывается, когда клиент называет цвет, ламинацию, форму, створки, тип открывания,
стеклопакет, фурнитуру, дополнительные комплектующие, бюджет, тип объекта, категорию продукции
или контактные данные.

Правила:

- передаются только те значения, которые клиент действительно сообщил; неизвестное остаётся пустым;
- уже известные сведения не затираются (пустые значения не перезаписывают State);
- значения проверяются по моделям `Preferences`, `ContextUser`, `ContactInfo`;
- инструмент не подтверждает наличие или совместимость компонентов — это задача каталога.

Инструмент возвращает обновлённый `user` и сообщение о сохранённых полях, поэтому является
единственным способом заполнения предпочтений клиента (отдельного узла извлечения нет).

## 6. Правила оркестрации

LLM самостоятельно определяет необходимость вызова инструментов, но все действия проверяются программной логикой.

Основные правила:

| Ситуация | Действие |
|---|---|
| Вопрос о конкретной продукции | `search_products` |
| Сравнение профильных систем | `search_products` |
| Подбор окна | `search_products` |
| Вопрос о гарантии | `search_knowledge` |
| Вопрос о монтаже или доставке | `search_knowledge` |
| Вопрос о продукции, требующий каталожных характеристик и дополнительной документации | Оба инструмента |
| Запрос на расчёт стоимости | `get_calculator_link` |
| Желание связаться с менеджером | `get_manager` |
| Клиент сообщает предпочтения, бюджет, тип объекта или контакты | `save_customer_profile` |
| Недостаточно данных для подбора | Уточняющий вопрос клиенту |
| Не требуется дополнительная информация | Ответ без вызова инструмента |

Инструменты не должны вызываться ради самого вызова.

Если информация уже присутствует в актуальном State и её достаточно для ответа, повторный поиск не требуется.

Если клиент задаёт несколько независимых вопросов, допускается вызов нескольких инструментов за один цикл.

Если инструмент вернул ошибку, агент должен корректно обработать её и не выдавать несуществующий результат.

## 8. Работа с клиентскими предпочтениями

Предпочтения клиента необходимо разделять на два типа.

### Обязательные ограничения (Hard Constraints)

Условия, которые вариант обязан удовлетворять.

Например:

- обязательный цвет;
- определённая форма;
- максимальный бюджет;
- конкретный тип открывания;
- обязательная конфигурация.

### Необязательные предпочтения (Soft Preferences)

Пожелания, по которым варианты можно сравнивать и ранжировать.

Например:

- более высокая теплозащита;
- повышенная звукоизоляция;
- больше естественного света;
- определённый внешний вид;
- оптимальное соотношение цены и характеристик.

Если клиент говорит «обязательно», это может стать ограничением.

Если клиент говорит «желательно», это предпочтение.

Алгоритм подбора сначала проверяет обязательные ограничения, а затем ранжирует подходящие варианты.

LLM отвечает за понимание естественного языка и извлечение предпочтений. Python отвечает за проверку данных, фильтрацию и ранжирование.

## 9. RAG и база знаний

RAG предназначен для хранения и поиска неструктурированной информации, которую неудобно представлять в виде колонок PostgreSQL.

Источниками могут быть:

- документация Melke;
- технические материалы;
- инструкции;
- статьи;
- информация о гарантии;
- условия заказа;
- материалы о монтаже и эксплуатации.

Документы разбиваются на фрагменты, преобразуются в embeddings и сохраняются в векторном хранилище.

При поиске агент получает наиболее релевантные фрагменты и использует их для формирования ответа.

Для документов желательно хранить метаданные:

- название документа;
- категория;
- название продукта или профильной системы;
- источник;
- ссылка на оригинал;
- дата или версия документа, если известна.

Конкретный выбор embedding-модели, векторного хранилища, размера чанков и алгоритма гибридного поиска фиксируется отдельно при реализации RAG.

### 9.1. Реализованная часть RAG: гибридный поиск

Реализован гибридный поиск: Dense + Sparse (BM25) + RRF. Reranker и пользовательский интерфейс поиска не реализованы.

Технологии:

- chunking — `RecursiveCharacterTextSplitter` (`langchain-text-splitters`), `chunk_size` 2000, `chunk_overlap` 300;
- embeddings — `Qwen3-Embedding-0.6B` (`sentence-transformers`), размерность 1024, нормализованные векторы, косинусная метрика; query instruction применяется только к поисковым запросам (на английском — так рекомендует карточка модели);
- Dense — PostgreSQL + `pgvector`, HNSW-индекс (`vector_cosine_ops`);
- Sparse — BM25 (k1 = 1.2, b = 0.75) по обратному индексу лексем; лексика нормализуется словарём PostgreSQL `russian`;
- объединение — Reciprocal Rank Fusion (`k` = 60);
- в модель передаётся 5–7 наиболее релевантных чанков (по умолчанию 6), у каждого есть текст, файл, раздел и URL источника.

Таблицы RAG:

`knowledge_documents` — реестр проиндексированных документов.

- `source_file` (PK) — имя файла в `knowledge_base/`;
- `content_hash` — SHA-256 содержимого на момент индексации;
- `chunk_count`;
- `indexed_at`.

`knowledge_chunks` — чанки и их векторы.

- `id` (PK);
- `source_file` (FK на `knowledge_documents`, `ON DELETE CASCADE`);
- `chunk_index`, `text`, `embedding` (`vector(1024)`);
- `source_url`, `category`, `product_name`, `section`, `page_number`;
- `token_count` — длина чанка в лексемах (dl для BM25);
- `metadata` (JSONB: `document_title`, `heading_path`, `source_urls`, `document_source_urls`);
- `created_at`, `updated_at`;
- уникальность `(source_file, chunk_index)`.

`knowledge_chunk_terms` — обратный индекс лексем для BM25: `chunk_id` (FK, `ON DELETE CASCADE`), `lexeme`, `tf`; уникальность `(chunk_id, lexeme)`, индекс по `lexeme`. Пополняется при индексации документа и удаляется вместе с его чанками.

Категории чанков соответствуют именам файлов базы знаний (`company`, `technology`, `products`, `installation`, `warranty`, `maintenance`, `ordering`, `delivery`, `faq`, `documents`) и используются как фильтр при поиске во всех каналах.

Индексация идемпотентна: документ переиндексируется только при изменении его хеша, старые чанки и их лексемы заменяются в одной транзакции. Запуск: `python -m rag.cli index`. Проверка поиска: `python -m rag.cli search "запрос" [--mode hybrid|dense|sparse] [--category ...]`.

RAG не должен использоваться вместо PostgreSQL для поиска точных структурированных характеристик каталога.

## 10. Формат ответа агента

Агент должен быть подготовлен к последующему подключению к backend и frontend.

Поэтому внутренний интерфейс агента должен возвращать структурированный JSON, а не только текст.

Backend будет использовать API агента для получения ответа и необходимых данных.

### Структура ответа

Пример реализованного формата:

```json
{
  "message": "Для ваших условий я бы рекомендовал рассмотреть Melke Evolution.",
  "status": "success",
  "actions": [],
  "handoff": {
    "contact": {"name": null, "phone": null, "email": null},
    "status": "not_requested",
    "additional_comment": null
  }
}
```

Назначение полей:

- `message` — текст ответа клиенту;
- `status` — результат обработки запроса: `success`, `no_results`, `error`;
- `actions` — дополнительные действия для клиента: `{type: "calculator_link", url: "..."}`;
- `handoff` — состояние передачи менеджеру: `status` (`not_requested`, `pending`, `completed`),
  контактные данные клиента и комментарий/причина обращения.

Поле `products` из первоначального наброска в контракт не входит (решение заказчика):
подобранные товары агент объясняет в `message`, а структурированный список товаров
в ответе backend пока не передаётся и может быть добавлен отдельной задачей.

Pydantic-модели ответа и результаты поиска находятся в `models.py` (`AgentResponse`,
`AgentAction`, `ResponseStatus`, `ActionType`, `ProductHit`, `KnowledgeHit`).

Не нужно возвращать внутренние рассуждения модели, системные промпты или техническую информацию, не предназначенную для клиента.

### Ответ в терминале

В обычном режиме терминал должен отображать только текст сообщения агента.

Например:

```text
Agent: Для ваших условий я бы рекомендовал рассмотреть Melke Evolution.
```

Технические данные, State и полный JSON не должны выводиться при каждом сообщении.

Для отладки необходимо предусмотреть специальные команды:

- `/state` — показать текущее состояние диалога;
- `/json` — показать полный JSON-ответ агента.

Эти команды предназначены только для локального тестирования и отладки.

Они не должны становиться частью обычного ответа клиенту или обязательной частью API.

## 11. Подготовка к Backend и Frontend

Агент должен быть реализован таким образом, чтобы его основную логику можно было использовать через backend без переписывания оркестрации.

Backend будет обращаться к API или публичному интерфейсу агента, передавать сообщение пользователя и идентификатор диалога, а затем получать структурированный ответ.

Основные данные взаимодействия:

**Вход:**

- идентификатор пользователя или диалога;
- сообщение клиента;
- при необходимости дополнительный контекст.

**Выход:**

- текст ответа;
- найденные товары;
- дополнительные действия;
- статус передачи менеджеру;
- технический статус обработки.

История диалога и State должны быть доступны по идентификатору диалога, чтобы пользователь мог продолжать разговор.

Текущая реализация может использовать локальный терминальный интерфейс для тестирования. Архитектура при этом не должна зависеть от терминала.

В будущем терминальный интерфейс заменяется или дополняется backend-интерфейсом, который использует ту же основную логику агента.

## 12. Обработка ошибок

Ошибки должны обрабатываться на уровне соответствующих компонентов.

Примеры:

- ошибка генерации JSON — отказ от выполнения поиска (§5.1), без повторного вызова модели;
- ошибка валидации — запрос не передаётся в БД;
- ошибка SQL — корректная обработка без раскрытия технических деталей клиенту;
- пустой результат поиска — сообщение об отсутствии подходящих вариантов;
- отсутствие релевантных документов RAG — сообщение об отсутствии подтверждённой информации;
- ошибка инструмента — агент сообщает, что сейчас не может выполнить действие.

Нельзя скрывать ошибки, которые мешают корректной работе приложения.

Нельзя сообщать клиенту об успешном выполнении действия, если инструмент не подтвердил результат.

## 13. Общие архитектурные принципы

1. LLM отвечает за понимание естественного языка, принятие решений в рамках оркестрации и формирование ответов.
2. Python отвечает за бизнес-логику, валидацию, фильтрацию, ранжирование и выполнение операций.
3. PostgreSQL хранит структурированные данные о продукции.
4. RAG предоставляет информацию из документов компании.
5. State хранит актуальный контекст диалога.
6. Инструменты выполняют конкретные операции и возвращают предсказуемые результаты.
7. Backend и frontend взаимодействуют с агентом через структурированный интерфейс.
8. Отсутствующие данные не заменяются предположениями.
9. Все характеристики и совместимость продукции должны иметь подтверждённый источник.
10. Архитектура должна оставаться простой и соответствовать масштабу MVP.

Принятые решения MVP:

- LLM — DeepSeek `deepseek-flash` через OpenAI-совместимый API (`langchain-openai`), ключ в `.env` (`DEEPSEEK_API`);
- предпочтения клиента сохраняются инструментом `save_customer_profile` (§5.5), отдельного узла извлечения нет;
- инструменты асинхронные: независимые вызовы одного хода выполняются параллельно (`ToolNode`),
  синхронные эмбеддинги и SQL вызываются через `asyncio.to_thread`;
- защита от зацикливания сверх стандартного `recursion_limit` LangGraph не добавлена (решение заказчика);
- передача менеджеру — заглушка (§5.4), история диалога не сохраняется в БД (§4).

Запуск: `python main.py`. Индексация базы знаний — `python -m rag.cli index`.
Backend — `uvicorn api:app --reload` (§16).

## 16. Backend (FastAPI) и стриминг

Backend — тонкая обёртка над публичным интерфейсом агента: `Agent.ask` / `Agent.ask_stream`.
Он не выбирает инструменты, не выполняет поиск и не меняет логику LangGraph.

### Сессии

Регистрации, авторизации и таблиц пользователей/истории нет (§4). Сессия нужна только
для сохранения контекста диалога и существует только в памяти процесса:
`sessions.SessionStore` хранит `session_id → Agent`, поэтому каждый диалог имеет
собственный `State`. Идентификатор — UUID4 (непредсказуемый, в логи не пишется).
После перезапуска приложения сессии теряются. Сообщения одной сессии обрабатываются
последовательно (`asyncio.Lock`), лимит одновременных сообщений — один на сессию.

### Эндпоинты

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/sessions` | Создание сессии, ответ `201` `{"session_id": "..."}` |
| `POST` | `/chat` | Сообщение агенту, ответ — `AgentResponse` (§10) |
| `POST` | `/chat/stream` | То же, ответ потоком SSE |
| `DELETE` | `/sessions/{session_id}` | Удаление сессии, ответ `204` |
| `GET` | `/health` | `{"status": "ok"}`, без обращения к БД и LLM |

Вход `/chat`: `{"session_id": "...", "message": "..."}`. Ограничения: `session_id` — до 64
символов `[A-Za-z0-9_-]`, сообщение — 1–2000 символов без учёта пробелов по краям, тело
запроса — до 16 КБ. Внешний вид ответа полностью совпадает с контрактом §10: `message`,
`status`, `actions`, `handoff`. Внутренний `State` и результаты инструментов наружу не отдаются.

### Стриминг

`POST /chat/stream` отвечает `text/event-stream`. События:

- `event: delta` — `{"text": "..."}` — часть текста ответа;
- `event: done` — полный `AgentResponse` (§10) — единственный источник истины: frontend
  заменяет накопленный текст на `message` из этого события;
- `event: error` — `{"message": "..."}` — сообщение об ошибке без технических подробностей.

Стримятся только текстовые фрагменты ответа агента; сообщения с вызовами инструментов
и внутренние рассуждения не транслируются.

### Ошибки

Формат тела ошибки: `{"error": {"code": "...", "message": "..."}}`.

| Ситуация | HTTP | `code` |
|---|---|---|
| Невалидный запрос, пустое или длинное сообщение, некорректный `session_id` | `422` | `invalid_request` |
| Слишком большое тело запроса | `413` | `request_too_large` |
| Неизвестная или удалённая сессия | `404` | `session_not_found` |
| Ошибка агента, DeepSeek или невалидный ответ агента | `502` | `agent_error` |
| Превышено время ответа агента (`AGENT_TURN_TIMEOUT`, по умолчанию 600 с) | `504` | `agent_timeout` |
| Агент не сконфигурирован (`DEEPSEEK_API`) | `503` | `service_unavailable` |
| Прочие исключения | `500` | `internal_error` |

Технические подробности пишутся в серверный лог, клиенту не возвращаются.
Ошибка инструмента внутри хода — не ошибка HTTP: агент возвращает `status: "error"` в контракте.

### Таймауты и первый запуск (почему первый ответ долгий)

`AGENT_TURN_TIMEOUT` — общий предел одного хода агента (600 с). Он с запасом перекрывает
холодный старт RAG: модель эмбеддингов `Qwen3-Embedding-0.6B` (~1.2 ГБ)
загружается лениво, внутри хода агента, при первом `search_knowledge`.
Замеры в контейнере: холодный кэш — **~298 с** (скачивание + загрузка),
тёплый кэш — **~4.5 с**. Сам ход агента на тёплом кэше — 4–9 с
(DeepSeek: 1–2 с на вызов, гибридный поиск: ~0.4 с).

Поэтому: кэш модели живёт в томе `hf-cache`; после пересоздания стека он не теряется.
Чтобы не ждать его во время диалога, модель можно прогреть один раз вручную:

```bash
docker compose exec app python -c "from rag.config import Settings; from rag.embeddings import Embedder; Embedder(Settings())"
```

Длительность каждого хода пишется в лог (`Ответ агента получен за N c`,
`Поток ответа агента завершён за N c`) при `LOG_LEVEL=INFO`.

### Перезапуск и подключение к БД

Перезапуск стека — `docker compose up -d` (идемпотентно: compose сам пересоздаёт контейнер
при расхождении конфигурации или состава сетей и переподключает его к сети проекта).

Инструменты держат долгоживущие подключения к PostgreSQL (`Catalog`, `HybridSearcher`),
поэтому в `tools.py` есть `_run_db_call`: при `psycopg.OperationalError`/`InterfaceError`
кэш подключений сбрасывается (`_reset_db_caches`) и запрос повторяется один раз.
Значит, `docker compose restart db` и пересоздание контейнера БД не требуют перезапуска
приложения — в логе будет `WARNING tools: Соединение с PostgreSQL потеряно, пересоздаю подключение`.
Модель эмбеддингов при этом не перезагружается: она кэшируется отдельно от подключения (`_embedder`).

Симптом `failed to resolve host 'db'` в логе означает, что контейнер БД выпал из сети проекта
(после ручных операций с сетями или очистки сетей); лечится тем же `docker compose up -d`.

### Запуск и развёртывание

- основной способ — `docker compose`: `docker compose up -d --build` (сервисы `app` и `db`, §16).
  Интерфейс и API открываются на `http://localhost:8000/`, PostgreSQL — на `localhost:5433`;
- на Windows без терминала: двойной клик по `start.cmd` в корне проекта — он делает
  `docker compose up -d`, ждёт `/health` и открывает `http://localhost:8000/` в браузере;
- в PowerShell / CMD (без прав администратора): `cd C:\путь\к\проекту` и `docker compose up -d`;
- в WSL (Ubuntu) нужна включённая интеграция Docker Desktop:
  Settings → Resources → WSL integration → включить дистрибутив. Без неё `docker` внутри WSL
  отвечает `The command 'docker' could not be found in this WSL 2 distro`, а `sudo docker`
  требует пароль и всё равно не работает: демон Docker Desktop живёт вне WSL;
- в Docker Desktop → Containers кнопка Start у группы проекта запускает уже существующие
  контейнеры (`compose start`) и не пересоздаёт выпавший из сети контейнер — для этого
  нужен именно `docker compose up -d` (или `start.cmd`);
- `app` — один процесс `uvicorn` (обязательно **один worker**: сессии в памяти), frontend
  раздаётся тем же приложением (`/`), поэтому CORS внутри compose не участвует;
  `CORS_ORIGINS` нужен только при выносе frontend на другой адрес;
- `db` использует существующий том с каталогом и индексом RAG; в сети compose к базе
  обращается по имени сервиса (`POSTGRES_HOST=db`), а значения `POSTGRES_HOST=localhost`
  и `POSTGRES_PORT=5433` в `.env` нужны для запуска с хоста (`python -m rag.cli index`,
  `uvicorn api:app`);
- модель эмбеддингов RAG скачивается при первом обращении к `search_knowledge` и кэшируется
  в томе `hf-cache`;
- без `docker compose`: `docker build -t melke-app .` и
  `docker run --env-file .env -p 8000:8000 melke-app`.

Ограничения MVP: сессии не переживают перезапуск, нет TTL и ограничения числа сессий,
стримингом передаётся только текст ответа (не `actions`/`handoff`), авторизации нет —
`session_id` фактически является секретом доступа к контексту диалога.

**Главный принцип проекта: LLM понимает клиента и управляет диалогом, Python контролирует данные и бизнес-логику, PostgreSQL хранит каталог, RAG предоставляет знания, а backend получает от агента структурированный результат.**
